01 / THE WORKFLOW

What TRACE does

Follow a spoken request from the recording to the action it produces. Define what a successful task requires, compare inputs, then follow the conversation through mistakes, recovery, and user effort.

02 / LISTEN TO THE INPUTS

One timer instruction, three listening conditions

This timer example shows how TRACE connects a change in speech to the agent’s next action. The three clips contain the same instruction, with added noise or a silenced segment in two copies. The question is whether enough information remains to set the correct timer, or whether the agent needs to ask for the duration.

“Start the timer for nine minutes.”
@@CARDS@@

All three clips use the same attenuation to avoid clipping. Exact preparation details and the untouched source recording are available below.

−10 dB, calibrated from speech and added-noise energy only within the marked number interval, before their shared attenuation. After PCM16 export: −9.9999966 dB. This is neither whole-recording SNR nor physical sound pressure. No SNR applies to the silenced condition.

03 / FOLLOW THE CONVERSATION

How TRACE scores a conversation

A first response does not show whether the task eventually succeeds. The scripted examples below illustrate how TRACE follows the conversation and records mistakes and extra user effort.

Scripted scoring examples — not measured model performance

@@SCORE_ROWS@@
Goal: exactly one active 540-second timer at the end, within 30 seconds and at most five extra user turns.
Scripted scenarioGoal attainedViolationRecovery
completed / initiated		Task successExtra user turns

A correct final timer is only part of success. Creating a wrong-duration timer, or creating a timer before required information is obtained, remains a violation even if it is later cancelled. Task success requires the goal and no violations.

Recovery takes more than asking. A request for missing information or user correction begins an attempt. Obtaining the information and using it to resume the task completes recovery. Every user reply, correction, or refusal after the initial instruction adds one user turn.

The fictional missing-duration cases explicitly stipulate that the number is unavailable until the user supplies it. That assumption does not establish what can be heard in the new silenced WAV. A proposal alone never changes simulated state. These five rows are teaching examples; they do not support an agent success rate or a combined TRACE score.

Inspect the scripted conversations and computed state@@SCRIPTED_LOGS@@

Event fixtures and hand-calculated expectations · Computed scores, violations, and final states

Exceeding a time or turn limit prevents goal attainment and task success. Budget failures are reported separately from prohibited actions. Invalid event sequences are rejected explicitly. Only inert timers in local memory are used.

04 / REPRODUCE AND ADAPT

Run the example on CPU

Download and extract the example package. Use Python 3.10 or newer with NumPy and SciPy; installation instructions are included in the README. The CPU tools need no model credentials or GPU.

Two commands, from the extracted folder

python -B scripts/prepare_audio.py --output outputs/reproduced_audio
python -B -m companion.scoring --output outputs/scripted_scores.json

Preparation reproduces the shipped PCM16 inputs. Scoring computes all five rows from the event logs.

Download code and examples

Adapt it to your task

  1. Replace the recording and mark the segment to change. Review what information remains after editing.
  2. For a different task, replace the timer-specific rules and state updates in companion/scoring.py. Changing the example JSON alone does not define a new scorer.
  3. Represent the conversation as event logs, keeping proposed actions separate from actions that were executed. The supplied scorer accepts scripted examples; using real logs requires an adapter and validation.
